# План: авто-декодер раскладки (рукей)

## Что строим

Программа перехватывает каждый `keyDown`, копит текущее слово и решает: пользователь
набирает в правильной раскладке или нет.

Если нет — **на лету**, не дожидаясь пробела: переключает раскладку и переписывает уже
набранный текст в правильный алфавит.

```
Пользователь жмёт клавиши h-e-l-l-o в русской раскладке
  → на экране: руддщ
  → программа срабатывает на префиксе «руд» (3 буквы)
  → гасит tap, стирает 3 символа, вставляет «hel» через keyboardSetUnicodeString
  → возвращает tap, переключает раскладку на US
  → пользователь допечатывает «lo» уже в английской → «hello»
```

Направления оба: русская раскладка → английское слово, и английская → русское.

Ключевое отличие от всех существующих решений: **срабатывание на префиксе, а не на
границе слова**. Все найденные аналоги ждут пробела/Enter. Это и достоинство
(мгновенная реакция), и главный источник риска (ложные срабатывания) — цифры ниже.

## Решение по платформе: standalone Swift, не Hammerspoon

Ты попросил поискать, может не стоит зависеть от других. Ответ: **стоит**, и выбор
не между «Hammerspoon или Swift», а между «зависимость или нет».

| | Hammerspoon 1.1.1 | Standalone Swift |
|---|---|---|
| Установлен | да | ничего ставить не нужно (Swift 6.4 + CLT есть) |
| Внешняя зависимость | да, стороннее приложение со своим lifecycle | нет, твой бинарник |
| Управление версиями | чужой релиз цикл | твой код |
| Умирает при падении | молча теряешь автозамену | твой crash, твои логи |
| Тестable логика | Lua, нужен зеркальный Python | тот же Swift, те же тесты |

**Решающий аргумент.** Задача — переписывать текст глобально. Для этого нужен
`CGEvent.tap` + Accessibility. Эта связка одинаково нужна в обоих вариантах, разницы
в привилегиях нет. А вот цена владения разная: Hammerspoon добавляет в цепочку чужой
процесс, который нужно отдельно запускать, перезапускать и отлаживать.

Существующие решения на Swift (проверены, работают) доказывают, что связка
`CGEvent.tap` + `TISSelectInputSource` + `keyboardSetUnicodeString` — это рабочая и
понятная комбинация на macOS 27, без костылей.

### Референс, который стоит прочитать перед кодом

`github.com/rundax/SwitchFix` — MIT, Swift, 122 коммита, активен (последний коммит
30 сентября 2026, релиз v0.0.10). Делает **ровно нашу задачу**: детектит слово в чужой
раскладке, стирает, переключает, перенабирает. Рабочая база для всего: `KeyboardMonitor`,
`InputSourceManager`, `TextCorrector`, `LayoutMapper`, `LayoutDetector`, `InputStateMachine`.

Их архитектуру берём. Их решение **ждать границы слова** — не берём, у нас другая
специфика (см. ниже).

Два открытых вопроса к нему, которые надо закрыть при чтении: `LICENSE` в корне
отсутствует, хотя README говорит MIT (проверить до копирования кода); в `TextCorrector`

### Источник словарей

`hermitdave/FrequencyWords` 2018 — проверен, отвечает 200:

```sh

curl -sL -o en_50k.txt https://raw.githubusercontent.com/hermitdave/FrequencyWords/master/content/2018/en/en_50k.txt
```

Формат: `слово частота`, разделитель — **пробел**, не таб. Размер 50000 строк каждый.
Локально на машине пригодного русского словаря нет (`/usr/share/dict/words` = web2, только
английский, 235k строк; `/usr/dict` не существует).

**Контаминация найдена.** В `ru_50k` 819 латинских записей, из них 123 двухбуквенные:
`the, i, you, a, to, s, b, o, t, and, it, that, of, c, in, l, me, no, m, we`.
Это английские обрезки в русском списке. Фильтр обязателен **для обоих языков**
(асимметричный фильтр — дефект: безопасный язык фильтруется, другой ломает ввод).

Второй слой фильтра — настоящий алфавит, а не только скрипт. Корпус содержит записи вида
`ƒа`, где `ƒ` это латиница, но не буква ни в одной раскладке; `isalpha()` её пропускает.

Результат сборки: **ru=47435, en=46691** слов.

### Правило срабатывания и порог

Два правила, каждое отмерено префиксным методом (по каждому нажатию, не по готовому слову)
на 1000 самых частых слов каждого языка:

**Правило A — целое слово:** переключаться, только если пере-декодированный префикс сам
является словом второго языка.

**Правило B — префиксное дерево:** переключаться, если пере-декодированный префикс является
началом какого-либо слова. Срабатывает раньше — внутри слова, а не после него.

| правило | порог | FP русский | FP английский | детекция | срабатывает внутри слова |
|---|---|---|---|---|---|
| A целое слово | L=3 | 2.10% | 0.50% | 96.1% | 75% |
| A целое слово | L=4 | 0.00% | 0.20% | 83.4% | 37% |
| B префиксное | L=3 | 2.90% | 2.50% | 96.1% | 87% |
| **B префиксное** | **L=4** | **0.00%** | **0.30%** | **83.4%** | **67%** |
| B префиксное | L=5 | 0.00% | 0.10% | 55.7% | 58% |

**Решение: правило B, порог L=4.** Единственная измеренная комбинация с нулём ложных
срабатываний на правильно набранном русском, которая при этом ловит 83% ошибок и
срабатывает до последней буквы в двух третях случаев.

Ложные срабатывания при L=3, которые L=4 подавляет: `вну→dye`, `дум→lev`, `куд→rel`,
`пре→ght`, `пут→gen`, `сег→ctu`, `смы→cvs`, `туд→nel`, `усп→ecg`.

**Методическая ошибка, которую пришлось исправить.** Первый замер брал выборку по алфавиту
(первые 1000 слов отсортированного файла) и дал 0.0% FP для правила B на L=4 с
указанием «правило B радикально лучше». Это было неверно: алфавитная выборка перекашивает
в сторону редких коротких слов. На выборке по частоте правило B на L=3 даёт 2.9% FP
против 2.1% у правила A — то есть хуже, а не лучше. Вывод переигран.

**Оговорка про методику.** Замер сделан зеркалом на Python, а не живым кодом на Swift.
По правилам скила зеркало годится для свипа корпуса, но его зелёный результат ничего
не доказывает про корабли. Цифры выше — обоснование порога, не подтверждение работы
программы. Реальные цифры получим только из тестов на реальном коде (задача 9).

## Проверка «слово не заменяется наполовину»

Требование: не допустить `tcь` — половина латиницей, половина кириллицей.

**Проверено: пере-декодирование само по себе смешанный алфавит произвести не может.**
Каждый выходной символ берётся из одной таблицы раскладки, значит весь результат
из одного алфавита. Смесь возникает только одним способом: программа стёрла префикс и
вставила часть, а пользователь допечатал хвост в момент, когда rewrite не был атомарным.

Значит защита — **атомарность, а не проверка строки**:

1. На срабатывании tap переходит в режим `suppress` и перестаёт писать в буфер.
2. Стирание N символов, вставка всего результата, переключение раскладки.
3. Только после завершения tap возвращается в режим `listen`.

Побочно это же решает и вторую гонку. Вставка идёт через
`CGEvent.keyboardSetUnicodeString`, а не через перенабор клавиш, поэтому **она не зависит
от того, успела ли переключиться раскладка**. Гонка «переключил, но первые буквы ушли в
старую раскладку → слово из двух алфавитов» в этой схеме невозможна по построению.
Это принципиально лучше, чем `hs`-подход с чтением раскладки перед каждой буквой.

## Отмена по Delete

Поведение, которое ты зафиксировал: Delete возвращает и текст, и раскладку, и программа
заглушает себя до конца слова.

Состояние отмены, которое нужно хранить:

| поле | зачем |
|---|---|
| `originalTyped` | исходный набранный текст (`руд`) |
| `replacementText` | во что превратили (`hel`) |
| `continuation` | что пользователь допечатал после срабатывания |
| `originLayout` | раскладка **до** переключения, не после |
| `active` | одноразовость, флаг снимается после первого Delete |
| `boundarySeen` | заглушить до пробела/Enter/пунктуации |

Арифметика — здесь ошибаются чаще всего. Клавиша Delete пользователя сама съела один
символ **до** того, как логика отмены увидела событие, поэтому:

```
стереть  = (fired - 1) + len(continuation)
вставить = fired + len(continuation)
```

Случай `continuation == 0` — первый, в который попадает пользователь, и именно его
пропускают тесты, написанные только на «пользователь допечатал дальше». Отдельный тест.

Плюс: отмена не должна срабатывать на чужих Delete. SwitchFix решает это эпохами
(`contextEpoch`, `correctionEpoch`, `editGeneration`) — сравнением счётчиков, а не
временем. Время врёт под нагрузкой. Беру их схему.

## Честно о границах

- **Боевая проверка — только твой живой ввод.** Синтетические key events не
  доставляются tap'у в том же процессе, поэтому автотест не может проверить реальное
  срабатывание. Проверка задач 5, 6, 10 — твои руки, не тесты.
- **Замер 12.4% → 2.1% сделан зеркалом на Python.** Это обоснование порога L=3, не
  доказательство работы программы. Настоящие цифры — задача 9.
- **2.1% FP — это 2 слова из каждых 100.** Откат по Delete существует именно ради них,
  он не опция.
- **`keyboardSetUnicodeString` не работает в Termius и Secure Input.** Там нужен
  фолбэк; проверить и зафиксировать поведение, а не молча пропускать.
- **Лицензия SwitchFix MIT заявлена в README, но файла `LICENSE` в репозитории нет.**
  Копировать код до выяснения нельзя.

## Среда: грабли, найденные на этой машине

**XCTest недоступен.** Полного Xcode нет, только Command Line Tools — модуль `XCTest` не
резолвится. Проект использует встроенный **swift-testing** (`import Testing`). Это не выбор,
а вынужденная мера.

**`swift test` после правки Swift-файла падает на первом прогоне:**

```
error: external macro implementation type 'TestingMacros.SuiteDeclarationMacro'
       could not be found for macro 'Suite'
```

Библиотека есть: `CommandLineTools/usr/lib/swift/host/plugins/testing/libTestingMacros.dylib`.
Плагин просто не подхватывается. Второй прогон подряд работает. Проверено на неизменённом
дереве: прогон 1 — 56 ошибок макросов, прогон 2 — настоящие результаты.
`tools/verify_runner.sh` это учитывает (ретрай до 3 раз только по этому конкретному
сбою, чтобы настоящее падение тестов никогда не маскировалось).

**`TISCreateInputSourceList` и `UCKeyTranslate` не thread-safe.** Параллельный прогон
тестов ронял процесс с SIGABRT. `LayoutLoader` закрыт `NSLock`.

**Восстановление файла не сбрасывает кэш сборки.** `cp` обратно + `touch` недостаточно:
нужен `swift build` перед `swift test`, иначе следующий прогон читает устаревший object
файл и рапортует ложный результат. На этом скрипт дважды показывал неверную «зелёную»
оценку — самый опасный вид ошибки в проверке.

**`set -e` в проверочном скрипте вреден.** Он убивает скрипт на первом ненулевом статусе,
включая те, ради которых скрипт написан. Шаги проверяют статус явно.
